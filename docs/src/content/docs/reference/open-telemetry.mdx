OpenTelemetry is the observability layer for GitHub Agentic Workflows. It lets workflows export traces and spans to an external backend, and it gives workflows a way to read that telemetry back when they need to inspect behavior across runs.

This guide covers the two ways gh-aw uses OpenTelemetry:

- [Write-side OTLP](#write-telemetry-through-otlp) sends new workflow spans to a backend such as Sentry.
- [Read-side MCP](#read-telemetry-through-mcp) lets a workflow query traces and spans that already exist in that backend.

Keep reusable telemetry setup in [shared workflow files](/gh-aw/reference/imports/) when multiple workflows use the same configuration.

## Write telemetry through OTLP

Configure [`observability.otlp`](/gh-aw/reference/frontmatter/#observability-observability) in workflow frontmatter when the workflow should emit new spans. A typical Sentry setup looks like this:

```aw wrap title=".github/workflows/daily-report.md"
---
network:
  allowed:
    - "*.sentry.io"
observability:
  otlp:
    endpoint:
      - url: ${{ secrets.GH_AW_OTEL_SENTRY_ENDPOINT }}
        headers:
          Authorization: ${{ secrets.GH_AW_OTEL_SENTRY_AUTHORIZATION }}
---
```

Once configured, gh-aw exports built-in workflow spans such as setup and conclusion events to the configured OTLP backend.

Use the bare secret expression for authorization headers, as shown above, rather than adding an authentication scheme prefix. For Sentry endpoints, gh-aw automatically rewrites `Authorization` to `x-sentry-auth`, so no prefix is needed.

OTLP header credentials of at least four characters are masked before setup exports spans, including encoded Basic-auth credentials, decoded passwords, and JSON-escaped values. Artifact and step-summary redaction also derives these values from the configured headers rather than relying on setup logs or recognizable token prefixes. OTLP endpoint and header environment variables, including multi-endpoint aggregated headers, are excluded from the eval agent sandbox.

If a credential was exposed in an earlier run, revoke or rotate it and remove the affected logs and artifacts. Updated redaction does not sanitize retained output from previous runs.

HTTP 401 and 403 export failures are not retried with unchanged credentials. Check the affected collector's configured authorization header and telemetry-write permissions. Transient delivery failures retain bounded retries; a rejected endpoint does not block other configured endpoints or the local telemetry mirror, and export failure does not fail the functional workflow.

### Protobuf encoding and Azure Monitor

The gh-aw JavaScript exporter defaults to OTLP/HTTP JSON (`http/json`) for traces and opt-in [compact session logs](/gh-aw/reference/compiler-enterprise-environment-controls/#unified-session-logs). Set the standard protocol environment variable to use binary OTLP/HTTP protobuf instead:

```yaml wrap
env:
  OTEL_EXPORTER_OTLP_PROTOCOL: http/protobuf
observability:
  otlp:
    endpoint: ${{ secrets.AZURE_MONITOR_OTLP_ENDPOINT }}
    headers:
      Authorization: ${{ secrets.AZURE_MONITOR_OTLP_AUTHORIZATION }}
```

`OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` and `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL`, when non-empty, take precedence over `OTEL_EXPORTER_OTLP_PROTOCOL` for their respective signals. A traces override does not affect logs, and a logs override does not affect traces. Set these overrides in workflow `env` when the signals need different encodings. All accept `http/json` or `http/protobuf`; gRPC is not supported by this helper. The selected encoding applies to all configured endpoints for that signal. Unsupported protocols and encoding errors produce an exporter diagnostic without retrying or silently falling back to JSON.

To manage the protocol as a repository, organization, or enterprise Actions variable, use `gh aw env get` and `gh aw env update`. The defaults file field `default_otlp_protocol` maps to the standard `OTEL_EXPORTER_OTLP_PROTOCOL` variable:

```bash
gh aw env get defaults.yml
```

Set this field in the downloaded file, retaining any other defaults:

```yaml
default_otlp_protocol: http/protobuf
```

```bash
gh aw env update defaults.yml --scope repo
```

As with other managed fields, setting it to `null` or omitting it deletes the variable at the selected scope. The compiler injects `${{ vars.OTEL_EXPORTER_OTLP_PROTOCOL }}` into workflow `env` unless that key is explicitly defined by the workflow. Recompile existing workflows once to add that lookup; subsequent variable updates take effect without recompilation.

For [Azure Monitor native OTLP ingestion](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/opentelemetry-protocol-ingestion), use the traces endpoint from Application Insights **OTLP Connection Info**, or construct the Data Collection Endpoint / Data Collection Rule path:

```text wrap
https://<logs-dce-domain>/datacollectionRules/<dcr-immutable-id>/streams/Microsoft-OTLP-Traces/otlp/v1/traces
```

The exporter retains a complete `/v1/traces` path, including query parameters. For base endpoints, it appends `/v1/traces`. Set `AZURE_MONITOR_OTLP_AUTHORIZATION` to the complete `Bearer <access-token>` header value for a Microsoft Entra identity authorized to write to the DCR (typically **Monitoring Metrics Publisher**). Provision and refresh that token outside this helper; protobuf encoding does not provide Azure authentication or make an Application Insights connection string an OTLP endpoint.

When compact session logs are enabled, the exporter selects the independent `Microsoft-OTLP-Logs` stream for the same DCE and DCR, preserving query parameters:

```text wrap
https://<logs-dce-domain>/datacollectionRules/<dcr-immutable-id>/streams/Microsoft-OTLP-Logs/otlp/v1/logs
```

The DCR must accept the logs stream as well as the traces stream. A complete logs endpoint is retained; generic collector endpoints use `/v1/logs` without Azure stream rewriting.

Protobuf requests use `Content-Type: application/x-protobuf` with binary-safe direct and proxy transports. Traces encode `ExportTraceServiceRequest`; logs encode `ExportLogsServiceRequest`, including structured bodies and trace/span correlation. The encoder uses only Node.js built-ins, and the sanitized local `otel.jsonl` trace mirror remains raw OTLP JSON regardless of wire encoding. These settings configure gh-aw JavaScript telemetry; external engines and the MCP gateway retain their own exporter capabilities.

Successful HTTP responses are inspected for OTLP `partialSuccess` in JSON or protobuf, for both traces and logs. JSON responses ignore unknown fields and treat `null` members as unset, following OTLP/ProtoJSON compatibility rules. Rejected spans or log records produce a warning with the signal-specific rejection count and increment `gh-aw.otlp.export_errors`; sanitized details appear in `gh-aw.otlp.export_error_details`. Warning-only partial success (zero rejected records with a collector message) warns without incrementing the error count. Collector messages are withheld because they may contain private data or credentials.

Response diagnostics are limited to 64 KiB. Malformed, unsupported, oversized, or unreadable successful responses record an exporter error with acceptance marked unknown. The proxy-aware curl transport has a 10-second request timeout within a 15-second subprocess deadline; a body timeout after known HTTP success reports unknown acceptance without retrying. Empty responses and valid full-success responses remain successful. None of these successful HTTP responses are retried: resending records the collector already accepted could create duplicates. Export diagnostics remain nonfatal and do not prevent delivery to other configured endpoints.

### Organization-wide defaults

When a workflow does not configure `observability.otlp` (in its own frontmatter or through an import), the compiler falls back to a default OTLP configuration read from the GitHub Actions environment:

| Name | Kind | Purpose |
| --- | --- | --- |
| `GH_AW_DEFAULT_OTLP_ENDPOINT` | Secret or variable | OTLP endpoint URL used when no endpoint is configured in frontmatter |
| `GH_AW_DEFAULT_OTLP_HEADERS` | Secret | Exporter headers (`key=value` pairs, comma-separated) sent to that endpoint |

Because both are resolved at run time, setting them at the repository or organization level enables telemetry for every agentic workflow without editing any workflow file.

Behavior:

- The endpoint secret takes precedence over the variable when both are set; clear both values to disable OTLP export.
- When both endpoint values are unset, the endpoint resolves to an empty string and OTLP export is a no-op.
- When an endpoint is set but `GH_AW_DEFAULT_OTLP_HEADERS` is empty, no span is exported to that endpoint from any job (setup, conclusion, outcome, or MCP gateway) — the runtime treats an endpoint without matching credentials as unconfigured rather than exporting unauthenticated telemetry. The agent job additionally fails with an error so the misconfiguration is visible instead of silently degrading to no telemetry.
- Any `observability.otlp` configuration in frontmatter or an import overrides these defaults entirely.
- If the workflow already defines any of the OTLP-related environment variables in its own `env:` block, the compiler skips injecting that specific variable instead of emitting a duplicate key.

Set variables with `gh aw env update` or `gh variable set`. Set either value as a secret with `gh secret set`.

### Google Workload Identity Federation

For Google Cloud Telemetry, configure Google Workload Identity Federation instead of a static authorization header. gh-aw mints and exchanges a GitHub OIDC token in every span-emitting job, and automatically grants those jobs `id-token: write`. The workload identity principal needs permission to write telemetry and, when `service-account` is set, permission to impersonate that service account.

Set `audience` to the workload identity provider resource name (`projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER`). gh-aw derives the GitHub OIDC audience (`https://iam.googleapis.com/...`) and the Google STS audience (`//iam.googleapis.com/...`) from it, so either fully-qualified form is also accepted.

```yaml wrap
observability:
  otlp:
    endpoint:
      - url: https://telemetry.googleapis.com
        headers:
          x-goog-user-project: ${{ vars.GCP_PROJECT_ID }}
    workload-identity:
      provider: google
      audience: ${{ vars.GCP_WIF_PROVIDER }}
      service-account: ${{ vars.GCP_SA_EMAIL }}
```

## Read telemetry through MCP

Configure [`mcp-servers`](/gh-aw/reference/frontmatter-full/) when the agent needs to inspect telemetry that already exists in the backend. A typical Sentry read setup looks like this:

```aw wrap title=".github/workflows/telemetry-investigation.md"
---
mcp-servers:
  sentry:
    command: "npx"
    args: ["@sentry/mcp-server@0.33.0"]
    allowed:
      - whoami
      - find_organizations
      - find_projects
      - get_trace_details
      - search_events
      - search_issues
    env:
      SENTRY_ACCESS_TOKEN: ${{ secrets.SENTRY_ACCESS_TOKEN }}
      SENTRY_HOST: ${{ env.SENTRY_HOST || 'sentry.io' }}
---
```

## Custom span attributes

`observability.otlp.attributes` attaches arbitrary key/value attributes to the job setup, job conclusion, and outcome summary spans:

```yaml wrap
observability:
  otlp:
    endpoint: ${{ secrets.OTLP_ENDPOINT }}
    headers:
      Authorization: ${{ secrets.OTLP_TOKEN }}
    attributes:
      deployment.environment: production
      langfuse.session.id: "{{ gh-aw.episode.id }}"
      langfuse.user.id: "{{ github.actor }}"
      catalogue.version: "${{ github.aw.metadata.version }}"
```

Values are plain strings. Template expressions such as `{{ gh-aw.episode.id }}` or `{{ github.actor }}` are resolved from attributes already computed for the span. Empty values are omitted. Values of at least 4 characters are masked in runner logs; shorter values are not masked.

Whole-value references in the form `${{ github.aw.metadata.<key> }}` resolve at compile time from the root workflow's top-level `metadata` map. They work in either custom attribute map, including in shared imported OTLP configuration, and support simple metadata keys such as `version`, `category`, and `owner`. The reference must occupy the entire attribute value; embedded references, nested selectors, missing metadata keys, and metadata values containing GitHub Actions expression delimiters are compile-time errors. Metadata remains string-only, and only explicitly referenced values are exported.

## Custom resource attributes

`observability.otlp.resource-attributes` appends additional resource attributes to the standard gh-aw and GitHub resource attribute set:

```yaml wrap
observability:
  otlp:
    endpoint: ${{ secrets.OTLP_ENDPOINT }}
    resource-attributes:
      service.namespace: platform-automation
      deployment.environment: ${{ github.ref_name }}
      catalogue.category: "${{ github.aw.metadata.category }}"
```

Use static strings or GitHub Actions expressions. Do **not** use `secrets.*` or `vars.*` values in `resource-attributes` because resource attributes are exported to external observability backends and are not treated as secret values.

## Built-in telemetry emitted by gh-aw

gh-aw emits a small set of built-in spans and trace artifacts once OTLP is configured.

These fields are a compatibility contract. gh-aw may add OpenTelemetry-standard aliases over time, but existing span names, environment variables, JSONL shape, and documented attributes remain available for dashboards and customer backends.

The built-in agent span uses OpenTelemetry [GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) for standard model, token, and finish-reason fields. gh-aw also adds a small number of gh-aw-specific fields.

You usually do not need to configure or memorize these built-in attributes. They are mainly useful when building backend queries, dashboards, or deeper debugging workflows. For the exhaustive built-in inventory, see the [OpenTelemetry attribute reference](/gh-aw/reference/open-telemetry-attributes/).

**Trace files and artifacts**

When observability is enabled, trace data is also mirrored to local JSONL files and uploaded in the `agent` artifact:

- `otel.jsonl` for spans emitted by gh-aw JavaScript helpers

Copilot CLI inherits the standard OpenTelemetry environment variables (`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`) and exports its own spans directly to the configured OTLP backend. Query them there, filtered by the `github.run_id` resource attribute (see [ADR-34450](https://github.com/github/gh-aw/blob/main/docs/adr/34450-inject-otel-resource-attributes-for-child-otel-sdk-correlation.md)).

See [Artifacts](/gh-aw/reference/artifacts/) for artifact download details.

## Custom spans from shared imports

Shared agentic workflow imports can emit their own OTLP spans alongside the built-in gh-aw telemetry. This lets third-party tools such as APM agents, data pipeline steps, and custom scanners attach their own measurements to the same distributed trace that gh-aw creates for each workflow run.

**Quick start**

The `otlp.cjs` helper provides a minimal, stable API. Use it in any `steps:` entry of a shared import:

`logSpan` is also re-exported unchanged from the public `actions/setup/js/index.cjs` entry point: `const { logSpan } = require(process.env.RUNNER_TEMP + "/gh-aw/actions/index.cjs");`. Existing direct imports from `otlp.cjs` remain supported.

```yaml wrap title=".github/workflows/shared/my-tool.md"
---
# My Tool — shared import that instruments its own telemetry

steps:
  - name: My Tool — do work and record telemetry
    id: my-tool-run
    uses: actions/github-script@v8
    with:
      script: |
        const path = require('path');
        const otlp = require(path.join(process.env.RUNNER_TEMP, 'gh-aw', 'actions', 'otlp.cjs'));

        const startMs = Date.now();
        // ... do your tool's work here (e.g. const result = await myTool.run()) ...
        const endMs = Date.now();

        await otlp.logSpan('my-tool', {
          'my-tool.version':         '1.2.3',
          'my-tool.items_processed': 42,
          'my-tool.result':          'success',
        }, { startMs, endMs });
---

My tool has run and its telemetry span will appear in the same distributed trace as the workflow run.
```

Import the shared file in any workflow alongside the OTLP configuration:

```yaml wrap title=".github/workflows/my-workflow.md"
---
on:
  schedule: daily
engine: copilot
imports:
  - shared/otlp.md
  - shared/my-tool.md
---

# Daily Report

Run the daily report using my-tool results.
```

**`logSpan` API**

```javascript
const path = require('path');
const otlp = require(path.join(process.env.RUNNER_TEMP, 'gh-aw', 'actions', 'otlp.cjs'));

await otlp.logSpan(toolName, attributes, options);
```

Here, `scalar` means `string`, `number`, or `boolean`.

`logSpan` is non-fatal and never throws. Export failures are surfaced as `console.warn`. When `GITHUB_AW_OTEL_TRACE_ID` is missing or invalid, the call returns silently.

**Recording an error span**

```javascript
await otlp.logSpan('my-scanner', {
  'my-scanner.items_scanned': 100,
}, { isError: true, errorMessage: 'database connection timed out' });
```

**Practical notes**

- Use `your-tool.` as a prefix for tool-specific attributes, for example `my-tool.items_processed`.
- Use [OpenTelemetry semantic conventions](https://opentelemetry.io/docs/specs/semconv/) for cross-cutting concerns, for example `db.system` and `http.response.status_code`.
- Avoid attribute names containing `token`, `secret`, `password`, `key`, or `auth`.

Attribute values are sanitized automatically before the payload is exported or mirrored. Matching secret-like keys are redacted, and very long string values are truncated. The same sanitization is applied to both OTLP export and the local JSONL mirror.

For debugging, every span emitted by `logSpan` is appended as a sanitized JSON line to `/tmp/gh-aw/otel.jsonl`, even when `OTEL_EXPORTER_OTLP_ENDPOINT` is not set. This file is included in the `agent` artifact when OTLP is enabled. Copilot CLI spans are not mirrored to a local file; they are exported directly to the configured OTLP backend and should be queried there.

```bash
# Download agent artifacts for a run
gh aw logs <run-id> --artifacts agent

# Inspect spans emitted by your tool
cat otel.jsonl | jq 'select(.resourceSpans[].scopeSpans[].spans[].name | startswith("my-tool"))'
```

  buildAttr, buildOTLPPayload, sendOTLPSpan,
  generateSpanId, SPAN_KIND_CLIENT,
} = require('/tmp/gh-aw/actions/send_otlp_span.cjs');

const traceId      = process.env.GITHUB_AW_OTEL_TRACE_ID;
const parentSpanId = process.env.GITHUB_AW_OTEL_PARENT_SPAN_ID;
const endpoint     = process.env.OTEL_EXPORTER_OTLP_ENDPOINT;

const setupSpanId = generateSpanId();
const querySpanId = generateSpanId();

await sendOTLPSpan(endpoint, buildOTLPPayload({
  traceId, spanId: setupSpanId, parentSpanId,
  spanName: 'my-tool.setup', startMs: t0, endMs: t1,
  serviceName: 'my-tool', kind: SPAN_KIND_CLIENT,
  attributes: [buildAttr('my-tool.phase', 'setup')],
  resourceAttributes: [buildAttr('my-tool.version', '1.2.3')],
}));

await sendOTLPSpan(endpoint, buildOTLPPayload({
  traceId, spanId: querySpanId, parentSpanId: setupSpanId,
  spanName: 'my-tool.query', startMs: t1, endMs: t2,
