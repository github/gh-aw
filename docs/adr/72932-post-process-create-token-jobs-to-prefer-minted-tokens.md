# ADR-72932: Post-Process Create-Token Jobs to Prefer Minted Tokens and Grant OIDC Permission

**Date**: 2026-10-29
**Status**: Draft
**Deciders**: pelikhan, Copilot coding agent (PR #72932), [TODO: verify]

---

### Context

Workflows can mint a short-lived GitHub token with a step whose id is `create-token`. This step usually uses OIDC. Authored frontmatter fields such as `github-token:` can already use mixed expressions like `steps.create-token.outputs.token || secrets.…`. Many token env bindings, however, are generated by the compiler in many separate emit paths, including `GH_TOKEN`, `GITHUB_TOKEN`, `GH_AW_GITHUB_TOKEN`, `GH_AW_GITHUB_MCP_SERVER_TOKEN` and `SECRET_GH_AW_GITHUB_TOKEN`. Those bindings stayed secrets-only. Jobs that minted tokens also lacked `id-token: write`. Consumers such as `elastic/oblt-aw` had to run a post-compile rewrite script to fix this (issue #72408). The fix must change only jobs that actually mint a token, rewrite only the steps after the mint step, keep custom credentials and existing fallback chains, and keep secret redaction working.

### Decision

We will add a single compiler pass, `wireCreateTokenJobs`, that runs after jobs are built and actions are resolved in `buildJobsAndValidate`. For each job whose steps contain an `id: create-token` step, the pass parses the steps YAML. It then rewrites each eligible default token env binding that appears after the mint step to `${{ steps.create-token.outputs.token || <original fallback chain> }}`. A binding is eligible only when its value is a single-line scalar made up only of `secrets.GH_AW_GITHUB_TOKEN`, `secrets.GH_AW_GITHUB_MCP_SERVER_TOKEN` and/or `secrets.GITHUB_TOKEN`. The pass also ensures `id-token: write` on that job. The edits are applied line by line to the original text, so the original step-fragment boundaries stay the same. When the pass rewrites `SECRET_GH_AW_GITHUB_TOKEN`, it also adds a `SECRET_GH_AW_GITHUB_TOKEN_FALLBACK` entry and a matching `GH_AW_SECRET_NAMES` entry, so redaction still covers the original secret. The main reason for this design is to fix every compiler-generated binding in one central place instead of changing each emit path.

### Alternatives Considered

#### Alternative 1: Change each emit path to produce minted-preferring expressions

Each code path that writes a token env binding (checkout manifest, lockdown or OAuth checks, MCP server config, redaction, and so on) could check for `create-token` and emit the combined expression directly. This avoids post-processing generated YAML and keeps the logic close to each binding. It was not chosen because the bindings are spread across many emitters. Each one would need to know whether its job mints a token and whether its step comes after the mint step. Every new emitter would also have to remember the rule, which makes regressions more likely.

#### Alternative 2: Leave the wiring to consumer post-processing or to frontmatter

Users could keep running external rewrite scripts, or set every token explicitly in frontmatter. This requires no compiler change. It was rejected because issue #72408 asks for exactly this behavior to be removed from consumers, and because frontmatter cannot reach compiler-generated bindings.

#### Alternative 3: Grant `id-token: write` and rewrite bindings for the whole workflow

The compiler could apply the permission and the token rewrite to every job whenever any job mints a token. This would be simpler, but it would point bindings at `steps.create-token` in jobs where that step does not exist and would grant OIDC permission more widely than needed. It was rejected because job-scoped least privilege is a stated requirement.

### Consequences

#### Positive
- A bare `gh aw compile` produces minted-preferring token bindings and `id-token: write` on minting jobs, so consumers can drop post-compile scripts.
- One pass handles all current and future compiler-generated default token bindings, and only within minting jobs, after the mint step.
- Custom credentials, explicit `steps.*` expressions and multi-line or block scalars are left unchanged, and existing fallback chains are kept.
- Redaction still covers the original secret through the added `*_FALLBACK` secret entry.

#### Negative
- The pass works on generated YAML text and parses it again. This couples it to the textual shape of emitted steps (single-line scalars, block-style env maps, and `key.Line` matching `value.Line`), which makes it more fragile than structured emission.
- Bindings that do not match the strict allowlisted forms, such as flow-style env maps, folded scalars or other secret names, are skipped without any warning.
- Compilation does extra work: each job containing `create-token` is parsed one more time.
- The list of eligible env names and secrets is hard-coded, so it must be updated when new default token bindings are added.

#### Neutral
- Jobs without a `create-token` step are unchanged, and repeated compilation is expected to produce no drift (covered by tests).
- Existing permissions are parsed and re-rendered on minting jobs, so their formatting in the lock file may change.
