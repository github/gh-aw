# ADR-79748: Replace work queue protocol v3 with time-free v4

> [!NOTE]
> Draft generated by the Design Decision Gate from PR #79748 evidence. Maintainers should complete the Context and Alternatives sections where the PR evidence is incomplete, then move the status out of Draft.

**Date**: 2026-11-24
**Status**: Draft
**Deciders**: Pending maintainer review

## Context

The work queue (`work-queue` branch, append-only `work-queue.jsonl`) coordinates smoke and other workflows through Work, Claims, Dispatches, and Completions. Protocol v3 had three problems, all reported in PR #79748 (fixes #79526):

- **Quiescence-gated policy.** v3 read pool limits from a Policy installed in the ledger. Policy can change only while the queue is quiescent. After #79146 raised `smoke-work-queue.concurrency` from 1 to 3 in `aw.json`, the queue held 72 `available` Work and never quiesced. The dispatcher pre-check then failed with `Installed smoke-work-queue Policy does not allow three Claims`. The dispatcher failed 8 consecutive runs from 2026-11-18.
- **Clock-based decisions.** Launch-correlation deadlines reported a worker as unverified even though it succeeded (run 42490135839). Clocks, not evidence, drove those outcomes.
- **Delivery verification that could stall.** Work pinned at `barrier: failed` after `DeliveryFailure verification_exhausted`, so a Work item could stop progressing without a new fact that justified it.

The v3 contract is recorded in [ADR-64955](64955-git-backed-work-queue-coordination.md) and its extensions, including [work-queue-protocol-upgrades.md](work-queue-protocol-upgrades.md) (status Superseded) and [ADR-76718](76718-durable-claim-delivery-evidence.md). Those records already point to v4 as their successor, but none of them records the v4 decision. This ADR fills that gap.

## Decision

Replace v3 with protocol v4 on the same branch and ledger format. v4 keeps replay deterministic and free of time, and drops the installed Policy, delivery verification, and run discovery:

- **No installed Policy.** Pool limits (`concurrency`, `per_account_limit`, `max_attempts`, approved profiles) come from the compiled `GH_AW_WORK_QUEUE_POLICY` environment on every run. A limit change takes effect with the recompiled workflow that carries it, not through a ledger Policy.
- **No time in decisions.** Replay never reads `at`. The protocol has no expiry, backoff, observation age, deadlines, or sleeps. CAS retries re-read the ledger up to 8 times without sleeping.
- **No delivery verification.** There are no barriers, `Result`, or `DeliveryFailure` records. A worker's `Completion` records the effects it applied. Effects are at-least-once: if a worker dies after applying an effect and before finishing, maintenance releases the Claim and the Work may run again.
- **Scheduler.** Work is ordered by priority, then submission order (FIFO), bounded by pool `concurrency` and optional `per_account_limit`. Each Dispatch takes one Claim.
- **Launch provenance.** The dispatcher sends `workflow_dispatch` at `target-ref`, verifies the created run (repository, workflow, event, and full `head_sha`), and commits `Dispatch{started, run_id, revision}`. If launch fails, it commits `Release{launch_failed}`. A worker binds only to its own run (`Bound`), and only when its run and checkout match the recorded revision.
- **Maintenance.** A scheduled maintenance run releases Claims whose bound run completed or whose dispatched run never appeared. It checkpoints after 512 lines.
- **Migration.** The first v4 dispatcher, producer, or maintenance run converts a v3 ledger whose head is a Checkpoint. `available` Work and its backing Issue carry over in FIFO order. Git history keeps the v3 log.
- **Breaking surface.** The `aw.json` keys, the `work-queue-policy` frontmatter, `dispatch-workflow.authorization`, `sync-issues`, and `work_queue_explain` are removed (see `.changeset/major-work-queue-v4-timeless.md`).
- **Formal model.** One bounded `WorkQueueV4.tla` replaces the 16 v3 models and 218 configs.

## Alternatives Considered

#### Keep v3 and drain the queue before changing pool limits

Keep the installed Policy and require quiescence before any limit change. Rejected: the smoke queue held 72 `available` Work and never quiesced, so a legitimate concurrency increase could not be applied at all.

#### Keep v3 clock-based verification and tune its deadlines

Keep launch-correlation deadlines and delivery barriers, and widen them. Rejected: the PR reports clock-driven false "unverified" outcomes (run 42490135839) and a barrier that pinned Work at `barrier: failed`. Widening deadlines moves the failure window without removing it.

#### Keep exactly-once effects through delivery barriers

Keep v3's barrier and `Result` path so each effect is verified before Completion. Not chosen in the PR: the v3 barrier path is the source of the stalled `verification_exhausted` state. The PR accepts at-least-once effects and documents the duplicate-run window instead. The inferred trade-off is that exactly-once delivery is not provided.

## Consequences

#### Positive

- Pool limit changes apply on the next run of the recompiled workflow. The dispatcher no longer blocks on quiescence.
- Replay is deterministic and clock-free. Launch and bind outcomes are judged from ledger records and the verified run, not from deadlines.
- The protocol surface shrinks: one bounded formal model replaces 16 models and 218 configs.

#### Negative

- Effects are at-least-once. A worker that dies between applying an effect and completing can cause its Work to run again.
- The change is breaking. Workflows, `aw.json`, frontmatter, and operator scripts that used removed keys must be updated together, and v3 ledgers must go through conversion.
- The smoke monitor judges Claims granted by the selected dispatcher attempt. It may read archived ledger segments from Git history (at most 6), which adds read-path complexity.

#### Neutral

- Native Go and JavaScript replay are kept in parity against regenerated v4 fixtures.
- Superseded ADRs (ADR-64955 and its extensions, ADR-76718) stay as historical records of v3.
