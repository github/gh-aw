# Webhook gateway security threat model

Generated by `check.py` from pinned TLC runs. Threat descriptions are human-authored; TLC supplies bounded invariant checks and counterexample traces, not automatic security discovery or a proof of implementation conformance.

## Assets, adversaries and trust boundaries

Assets are source confidentiality, dispatch authority, approved workflow configuration, durable replay state, and runtime continuation. Adversaries include unauthenticated senders, authenticated but unenrolled tenants, payload authors, unrelated Apps/human dispatchers, and stale/concurrent workers. Network failure and restart are nonmalicious faults with security consequences. Protected enrollment, GitHub-owned context, provider/JWT verification, the compiler and durable storage primitives are trusted.

The modeled path is provider -> authenticated enrollment/predicate evaluation -> durable receipt and immutable projection -> fenced dispatch authorization -> GitHub Actions -> App provenance -> server OIDC/hash/artifact admission -> correlated continuation -> local envelope validation -> agent. Discovery is a separate, generation-fenced control plane. Resource URLs and subscription selectors confer no provider-read or dispatch authority.

## Checked scope and result

TLC 2.19, official TLA+ Tools v1.7.4, SHA-256 `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`. The secure model exhausted **23,620 distinct states** (81,295 generated; zero queued) with all 18 invariants satisfied.

Bounds: 13 request profiles; one source/destination/subscription receipt key; two possible content fingerprints represented by original/conflicting receipt actions; two workers and fencing generations; at most two dispatch attempts; one irreversible approval revocation and one restart. The initial table represents an independently verified snapshot, except for the incomplete-discovery profile. A scan can overlap revocation. Execution-version, signature, projection and response validity are finite predicates, not implementations of parsers or cryptography.

No fairness or liveness property is asserted. Terminal, denied and quarantined states are intentional; deadlock checking is disabled. Counters track GitHub acceptance, not successful workflow execution. The at-most-one-acceptance invariant depends on quarantining every uncertain outcome and does not provide exactly-once delivery or reconcile quarantined work. Every transmit represents a durably recorded attempt.

## Threats and control sensitivity

Each row disables exactly one modeled protection. An expected invariant failure demonstrates control sensitivity, **not an exploitable defect in current code**. Receiver and server rows describe external integration requirements; no such service ships in this repository. Destination rows abstract shipped checks.

| Control mutation | Threat | Required mitigation | Boundary | Expected violated invariant |
| --- | --- | --- | --- | --- |
| `source-auth` | Spoofed provider delivery | Authenticate original provider evidence before durable admission. | receiver | `SourceAuthenticated` |
| `source-binding` | Cross-tenant confused deputy | Bind authenticated evidence to independently approved source enrollment. | receiver | `SourceEnrolled` |
| `predicates` | Unmatched event activates a workflow | Evaluate complete original predicates before projection. | receiver | `PredicatesMatched` |
| `projection` | Native content or credentials leave ingress | Persist and transmit only the declared minimal projection. | receiver | `MinimalDispatch` |
| `incomplete-scan` | Incomplete inventory activates routes | Publish only complete, validated repository snapshots. | receiver | `CompleteDiscovery` |
| `stale-publication` | Slow refresh resurrects revoked routes | Fence publication against approval and invalidation generations. | receiver | `FencedPublication` |
| `dispatch-recheck` | Queued work dispatches after revocation | Recheck current bindings at every local dispatch authorization point. | receiver | `CurrentDispatchAuthorization` |
| `token-scope` | Overprivileged installation token | Require the approved destination installation and minimum token scope. | receiver | `ScopedDispatchToken` |
| `worker-fence` | Stale worker transmits | Durably fence competing worker leases before authorizing a send. | receiver | `FencedWorker` |
| `conflicting-replay` | Same delivery identity overwrites content | Bind the scoped receipt key to immutable authenticated content. | receiver | `ImmutableReceipt` |
| `retry-uncertain` | Lost response causes duplicate dispatch | Quarantine uncertain outcomes instead of automatically retrying. | receiver | `AtMostOneAcceptance` |
| `forget-receipt` | Restart loses accepted-delivery tombstone | Retain durable receipt and outcome records across restart. | receiver | `AtMostOneAcceptance` |
| `app-provenance` | Human or unrelated App bypasses ingress | Verify GitHub-owned original actor and the independently bound App/bot. | destination | `AppProvenance` |
| `oidc` | Unverified OIDC identity gains continuation | Verify issuer, signature, audience, time and signed run/job claims server-side. | server | `SignedAdmission` |
| `hash` | Stale workflow configuration gains continuation | Require the signed audience hash to match independently verified configuration. | server | `HashBoundAdmission` |
| `artifact` | Copied configuration hash blesses edited code | Verify the actual artifact at the signed revision, not just its hash header. | server | `ArtifactBoundAdmission` |
| `response` | Wrong run or credential-bearing response continues | Accept only the closed 200 response echoing every request field with allowed=true. | destination | `CorrelatedContinuation` |
| `envelope` | Malformed dispatch reaches the agent | Validate the closed v2 envelope and compiled subscription before activation. | destination | `ValidatedActivation` |

## Nonvacuity witnesses

The secure model also deliberately checks the negation of reachable behavior. These are expected witness failures while all security invariants remain enabled.

| Witness invariant | Meaning | Distinct states explored before witness |
| --- | --- | --- |
| `NoAgent` | A valid delivery reaches the agent. | 9,885 |
| `NoUncertainty` | A transmitted dispatch can become uncertain. | 420 |
| `NoKnownRetry` | Known nonacceptance permits a second attempt that is accepted. | 4,028 |
| `NoDuplicate` | A duplicate receipt is recognized without new admission. | 67 |
| `NoConflict` | A conflicting duplicate is rejected without replacing its content. | 68 |

## Implementation mapping and residual risk

The normative mapping is the linked gateway specification's discovery, durability, App provenance, getToken admission and envelope sections. Shipped destination checks are `verifyGatewayProvenance` in `actions/setup/js/check_gateway_provenance.cjs`, `verifyGatewayAdmission` in `check_gateway_admission.cjs`, `validateWebhook` in `validate_webhook.cjs`, and `normalizeWebhookContext` in `webhook_context.cjs`. Source hashes are observations, not a refinement proof or runtime regression test.

The source-authentication predicate assumes a reviewed profile binds native discriminators and stable delivery identity to authenticated evidence. HMAC over body bytes alone need not authenticate event/delivery headers. This model does not establish retry stability, multi-tenant namespace uniqueness, a safe tombstone retention horizon, or collision resistance. Batch-local URL/item deduplication cannot replace durable delivery replay protection.

Known revocation prevents later local authorization; it cannot recall an already authorized/transmitted request or an issued continuation. The model stores checks at their ordering point rather than incorrectly requiring approvals to remain true forever. GitHub selects the execution revision; discovery does not pin it. Exact signed-revision verification and explicit older-attempt policy remain server responsibilities; full refresh reconciliation and revision rollback behavior are not modeled.

Unmodeled risks requiring integration tests/review: real signature/JWKS and canonical-URL parsing; exact byte/numeric/predicate budgets; multi-delivery batching and source-isolation keys; repository transfers and listener collisions; stale cache expiry and unavailable discovery; resource exhaustion/DoS; SSRF/redirect and credential leakage; provider read authorization; adversarial prompt content; cleanup/revocation of runtime-minted tokens; compromised central/App credentials; arbitrary custom steps and abrupt runner termination. An approved App identifies a principal, not a tenant or CAO process. A configuration hash is not a whole-file digest. A GitHub 204 proves acceptance only. None of these omissions is evidence of safety or a discovered implementation vulnerability.
